# Fifty-question architecture review

This review distinguishes protocol behavior and architectural recommendations from implemented guarantees. See status.md
and failure-analysis.md for evidence and unresolved risks.

| # / Question                         | Reasoning, protocol behavior and implementation                                                                                                                                          | Failure behavior, security implications and trade-offs                                                                                                                                                                                            |
|--------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 1. Central IAM design                | Modular AS/OP and directory with separate RS enforcement; split PDP only when measured demand warrants. A primary consistency domain owns refresh families.                              | Extra services improve isolation but introduce network failure and coordination.                                                                                                                                                                  |
| 2. Authentication vs authorization   | AuthN establishes subject; AuthZ evaluates action/resource under current policy. A valid login alone grants no business operation.                                                       | Stale claims or trusting caller-selected subject creates elevation.                                                                                                                                                                               |
| 3. OAuth2 vs OIDC                    | OAuth delegates API access; OIDC adds ID tokens, identity claims, discovery and UserInfo. APIs accept access tokens, not ID tokens.                                                      | Token substitution fails when type, audience and scope are enforced.                                                                                                                                                                              |
| 4. AS vs RS                          | AS authenticates clients and issues tokens; RS validates and enforces access for its own API.                                                                                            | Local validation decouples availability but delays revocation.                                                                                                                                                                                    |
| 5. Code with PKCE                    | Client stores verifier/state/nonce, sends S256 challenge, receives short-lived code, exchanges with verifier and client binding.                                                         | A stolen code alone cannot be redeemed without the verifier; malicious client/device compromise remains.                                                                                                                                          |
| 6. Implicit grant                    | Front-channel bearer delivery expands leakage and replay exposure; code + PKCE confines token exchange to protected transport.                                                           | No implicit registration exists here.                                                                                                                                                                                                             |
| 7. Password grant                    | Client handling user passwords defeats federation/MFA boundaries and encourages credential exposure.                                                                                     | Use redirects/system browser; no password grant registration exists.                                                                                                                                                                              |
| 8. OIDC SSO                          | Each RP starts its own authorization request; OP reuses an eligible session and issues a distinct code/token set.                                                                        | Freshness, consent and MFA policy can force reauthentication; never share unrelated app tokens.                                                                                                                                                   |
| 9. OIDC vs SAML                      | OIDC uses OAuth redirects and JWT identity assertions; SAML commonly uses XML assertions and browser POST bindings.                                                                      | Use maintained libraries for XML/signature validation; SAML is out of scope here.                                                                                                                                                                 |
| 10. RP-initiated logout              | RP supplies a valid ID-token hint and registered post-logout URI to OP logout; OP ends its session.                                                                                      | Validated OP logout revokes session refresh families and enqueues durable SID-specific back-channel delivery; opted-in RPs invalidate shared sessions after verification. Unreachable/unregistered RPs and terminal failures can retain sessions. |
| 11. JWT after logout                 | JWT signatures remain valid independently of browser session state. Offline validators accept until expiry/skew.                                                                         | Short TTL limits exposure; introspection or coordinated denylist adds stronger revocation dependency.                                                                                                                                             |
| 12. Secure sessions                  | Redis browser contexts with authoritative PostgreSQL idle/absolute deadlines, CSRF-eligible browser renewal, atomic grant revocation/logout enqueue, cookie flags and login ID rotation. | Redis outage fails session-backed paths; theft of a valid cookie still requires containment.                                                                                                                                                      |
| 13. Session fixation                 | Attacker preselects a session ID reused after login. Spring changes the ID on authentication.                                                                                            | Verify with a real browser/session test; copied authenticated cookies are session hijacking instead.                                                                                                                                              |
| 14. CSRF                             | Framework form tokens protect browser POSTs; OAuth state binds response to the initiating client session.                                                                                | Nonce protects OIDC response replay; PKCE and CSRF tokens have distinct responsibilities.                                                                                                                                                         |
| 15. Password hashing                 | Adaptive library BCrypt cost 12 with generated salts; tune on deployment hardware and validate byte limits.                                                                              | Memory-hard Argon2id is an alternative; password hashing cost is both protection and DoS capacity input.                                                                                                                                          |
| 16. Credential stuffing              | Rate limits, generic failures, edge abuse controls, MFA and breached-password screening reduce success.                                                                                  | Distributed botnets and targeted account denial persist; monitoring and screening are incomplete here.                                                                                                                                            |
| 17. TOTP                             | Shared secret and time step yield a short code through an established library; store secret encrypted and consumed step durably.                                                         | Single-step validation reduces tolerance; TOTP remains phishable and depends on synchronized clocks.                                                                                                                                              |
| 18. WebAuthn phishing resistance     | Credentials bind signatures to RP ID/origin and a fresh challenge; verifier checks ceremony, user presence/verification and signature.                                                   | Yubico 2.10.1 verifies real browser ceremonies; durable challenges, exact origins and UV are required. See passkeys.md and hardware-attestation.md for opt-in offline metadata trust; no new assurance claim or physical-vendor certification.    |
| 19. Lost MFA device                  | One-time high-entropy recovery codes are hashed and consumed atomically; stronger recovery should reverify identity and notify.                                                          | Helpdesk/social engineering remains a major bypass risk; full recovery lifecycle is unfinished.                                                                                                                                                   |
| 20. JWT vs opaque                    | JWT verifies locally; opaque token introspection consults server state.                                                                                                                  | JWT has claim/revocation staleness; opaque increases latency and dependency availability requirements.                                                                                                                                            |
| 21. JWT validation claims            | Trusted issuer/key, RS256, type, exp/nbf with bounded skew, exact API audience and applicable scope/subject semantics.                                                                   | Unknown kid fails; never trust token-provided key locations.                                                                                                                                                                                      |
| 22. Signature alone insufficient     | A correctly signed token may target another API, represent an ID token or lack permission for this resource.                                                                             | Separate token validity from policy decision and authoritative tenant/resource checks.                                                                                                                                                            |
| 23. JWKS discovery                   | Trusted issuer publishes public keys; validator selects allowed-algorithm key by kid and caches keys.                                                                                    | Unknown keys may trigger a bounded refresh; unavailable new keys fail closed.                                                                                                                                                                     |
| 24. Key rotation                     | Deploy new signing key and overlap old public keys until old tokens and caches expire.                                                                                                   | Inconsistent replica keysets break validation; tested verifier overlap does not prove operational automation.                                                                                                                                     |
| 25. Key compromise                   | Stop compromised issuance, replace keys, revoke state and evict verifier caches through coordinated operations.                                                                          | Asynchronously cached public keys can continue accepting forged tokens until eviction.                                                                                                                                                            |
| 26. Refresh rotation                 | Each successful exchange persists a new generation before subsequent use; history links generations to one authorization.                                                                | The fixed family deadline caps each generation; bounded automatic retention now uses a durable creation floor.                                                                                                                                    |
| 27. Refresh replay detection         | Authenticated client presents an old digest; serialize by family and revoke current authorization.                                                                                       | Strict semantics also revoke on legitimate concurrent use/lost response; clients must single-flight.                                                                                                                                              |
| 28. JWT revocation                   | Offline JWTs require expiry or extra authoritative revocation enforcement.                                                                                                               | Denylist/introspection costs state, propagation and availability; do not promise instantaneous global removal.                                                                                                                                    |
| 29. Introspection vs revocation      | Introspection queries active state; revocation changes server token state.                                                                                                               | A resource server that only checks JWT signatures does not automatically observe revocation.                                                                                                                                                      |
| 30. Client Credentials               | Registered confidential workload authenticates and requests preauthorized scopes for the target audience.                                                                                | Secrets must rotate, remain out of logs and never substitute for a human identity.                                                                                                                                                                |
| 31. private_key_jwt or mTLS          | Asymmetric client authentication removes shared secret custody or binds clients to certificates.                                                                                         | Audience/replay checks, trust anchors and rotation are essential; these modes are not configured here.                                                                                                                                            |
| 32. Audience confusion               | Issue a narrowly targeted aud and validate it independently in each resource server.                                                                                                     | Generic multi-service tokens expand blast radius; a signature trusted across services is not enough.                                                                                                                                              |
| 33. RBAC vs ABAC                     | RBAC maps roles to permissions; ABAC adds trusted subject/resource/context predicates.                                                                                                   | Avoid ad hoc general policy languages; owner/tenant/assurance cannot come from untrusted JSON.                                                                                                                                                    |
| 34. PDP and PEP                      | PDP returns deterministic default-deny decisions; PEP enforces them at business operations.                                                                                              | PDP outage must deny high-risk actions; sample orders has scope PEP but no resource PDP integration yet.                                                                                                                                          |
| 35. Resource permissions             | Join actual resource tenant, current membership and resource-scoped role grants for the validated subject.                                                                               | Authorization and business mutation can race; high-risk workflows need stronger transaction/fencing semantics.                                                                                                                                    |
| 36. Privilege escalation             | Separate platform and tenant authority; prevent ordinary clients gaining admin scopes; authorize every management operation.                                                             | Insider misuse needs dual control/audit/step-up; current human administration remains incomplete.                                                                                                                                                 |
| 37. Multi-tenant security            | Shared issuer with current authoritative membership/resource tenant checks, not a token tenant claim alone.                                                                              | Separate issuers/deployments improve isolation at greater operational cost.                                                                                                                                                                       |
| 38. Cached decisions                 | Key by identity/action/resource and versions; bounded TTL/invalidation with clear staleness.                                                                                             | Current PDP does not cache; strong fresh decisions cannot rely on disconnected stale ALLOW.                                                                                                                                                       |
| 39. Revocation propagation           | Publish versioned durable invalidation to PEPs, with TTL bounding missed delivery.                                                                                                       | A durable outbox now propagates RP-session logout; general PEP revocation events remain absent. Offline JWTs rely on expiry and fresh PDP where integrated.                                                                                       |
| 40. Enterprise federation            | Validate trusted issuer/audience/keys through maintained OIDC/SAML integration; map issuer + subject.                                                                                    | Upstream outage fails new auth; federation is a documented extension, not implemented.                                                                                                                                                            |
| 41. Account linking risks            | Email-only matching can link attacker-controlled accounts; require authenticated proof of both identities and explicit policy.                                                           | Unexpected assertions and issuer collisions must fail closed; no linking adapter exists here.                                                                                                                                                     |
| 42. SCIM                             | Authorized provisioning clients use SCIM resource operations, filtering, pagination and idempotent updates/deprovisioning.                                                               | Full conformance and revocation integration must be tested; no SCIM endpoint is claimed.                                                                                                                                                          |
| 43. Secure administration            | Dedicated auth audience/scope, validation, bounded responses, version preconditions and least privilege.                                                                                 | Current APIs are a constrained subset; idempotency, human step-up and complete OpenAPI are missing.                                                                                                                                               |
| 44. Privileged audit                 | Record actor, target, operation, outcome, timestamp, policy version and correlation without credentials.                                                                                 | Transactional outbox/tamper-aware export is required for durable assurance; selected SQL events are insufficient.                                                                                                                                 |
| 45. AS unavailable                   | New auth/token requests fail; resource validation may continue on eligible existing JWTs.                                                                                                | Opaque introspection paths depend on AS availability; never universally fail open.                                                                                                                                                                |
| 46. Offline validation during outage | Cached trusted public keys validate unexpired tokens with issuer/audience/type/scope checks.                                                                                             | Unknown kid or expired JWT fails; key compromise cannot be instantly observed offline.                                                                                                                                                            |
| 47. One million decisions/sec        | Measure local policy snapshots versus remote PDP separately; partition by tenant and scale immutable readers.                                                                            | SQL per remote decision is not demonstrated at that scale; policy freshness and CPU/network costs dominate.                                                                                                                                       |
| 48. Multi-region replay consistency  | Give each token family a fenced home writer or globally consistent transactional store.                                                                                                  | Asynchronous multi-master replication alone admits dual winners and cannot prove safe rotation.                                                                                                                                                   |
| 49. Protocol/security tests          | Use real HTTP authorization/token requests, malicious redirect/PKCE/code reuse, race tests and tenant fixtures.                                                                          | Mocks/scanners complement actual flows; conformance, ZAP and penetration tests remain outstanding.                                                                                                                                                |
| 50. Production evidence              | Reproducible builds, dependency/security review, full acceptance tests, failure drills, load measurements, key/recovery operations and independent review.                               | A passing development login is insufficient; this baseline does not meet the complete production definition of done.                                                                                                                              |
